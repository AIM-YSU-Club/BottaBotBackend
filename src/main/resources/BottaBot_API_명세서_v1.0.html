1. 개요 및 공통 사항

요구사항정의서의 기능 요구사항(MEM/SRC/NB/CHAT/NOTI)을 기준으로 Spring Boot 기반 REST API 스펙을 정의합니다. 인증은 JWT(Access/Refresh Token) 방식을 기준으로 설계했습니다.

Base URL

https://api.bottabot.com/api/v1

인증 방식

  • 로그인 성공 시 Access Token(단기), Refresh Token(장기) 발급
  • 인증이 필요한 요청은 Authorization: Bearer <accessToken> 헤더 필요
  • Access Token 만료 시 401 UNAUTHORIZED + TOKEN_EXPIRED 반환 → 클라이언트는 Refresh API 호출

공통 응답 포맷

{
  "success": true,
  "data": { // 실제 응답 데이터 },
  "error": null
}

// 실패 시
{
  "success": false,
  "data": null,
  "error": {
    "code": "SOURCE_TOO_LARGE",
    "message": "파일 크기는 50MB를 초과할 수 없습니다."
  }
}

공통 에러 코드

HTTP Statuscode설명
400INVALID_REQUEST요청 파라미터/본문 유효성 오류
401UNAUTHORIZED / TOKEN_EXPIRED인증 실패, 세션(토큰) 만료
403FORBIDDEN권한 없음(타인 노트북 접근 등)
404NOT_FOUND리소스 없음
409DUPLICATE_EMAIL이메일 중복 등 충돌
413SOURCE_TOO_LARGE파일 50MB 초과
422SOURCE_LIMIT_EXCEEDED노트북당 소스 50개 초과
422URL_CRAWL_FAILEDURL 크롤링 차단/실패 (우회 처리 없이 실패 반환)
500INTERNAL_ERROR서버 내부 오류

페이지네이션 (목록 조회 공통 쿼리)

sizeint페이지 크기 (기본 20)
sortstring예: updatedAt,desc

4-1. 소스 업로드

Method / Path설명요청응답비고
POST
/notebooks/{notebookId}/sources/files		 파일 업로드 (PDF/DOCX/TXT/PPTX/XLSX) multipart/form-data: file*, fileName(선택), memo(선택) sourceId, status=PENDING P1 SRC01_UPLOAD01 — 파일당 50MB, 노트북당 50개 제한
POST
/notebooks/{notebookId}/sources/url		 URL 소스 추가 (크롤링) url* sourceId, status=PENDING, (자동 감지) title P1 SRC01_UPLOAD02 — 크롤링 차단 시 우회 없이 URL_CRAWL_FAILED 반환
POST
/notebooks/{notebookId}/sources/text		 텍스트 직접 입력 content*, title(선택) sourceId, status=PENDING P2 SRC01_UPLOAD03

4-2. 소스 처리/조회/삭제

Method / Path설명요청응답비고
GET
/notebooks/{notebookId}/sources		 소스 목록 조회 (처리 상태 포함) Path: notebookId 소스 목록: id, name, type, status(PENDING/PROCESSING/DONE/ERROR) P2 SRC02_PROC04
GET
/notebooks/{notebookId}/sources/{sourceId}/status		 단일 소스 처리 상태 실시간 조회 (SSE) Accept: text/event-stream status 변경 이벤트 스트림 (대기→처리중→완료/오류) P2 (추가 제안: 폴링 대신 SSE 권장)
DELETE
/notebooks/{notebookId}/sources/{sourceId}		 소스 삭제 (벡터 DB 임베딩 함께 삭제) Path: sourceId 204 No Content P1 SRC02_PROC03
내부 처리 파이프라인 (비동기, Async/Queue 기반)
업로드 접수 → Docling으로 문서 파싱 → Markdown 변환 → 청크 분할(기본 512자) → 임베딩 API 호출 → 임베딩 벡터를 Vector DB에 저장 → status DONE 갱신. 이 파이프라인은 사용자에게 직접 노출되는 API가 아니라 내부 워커(예: Spring @Async 또는 별도 워커 서버)에서 처리되는 것을 권장합니다.

/notebooks/{notebookId}/chat-sessions		 대화 세션 목록 조회 Path: notebookId 세션 목록 (제목/최근 메시지/updatedAt) P1
DELETE

GET
/chat-sessions/{sessionId}/messages		 대화 히스토리 조회 (맥락 유지용) Query: limit(기본 최대 유지 턴수 10) 메시지 목록 (role, content, citations) P1

처리 흐름: 질문 수신 → 임베딩 변환 → Vector DB 유사도 검색(Top-K 청크) → 대화 히스토리(최대 N턴)와 함께 LLM 프롬프트 구성 → 스트리밍 응답 생성 → 응답 내 인용된 청크의 출처 메타데이터를 함께 반환.

8. 추가 제안 사항 정리

요구사항정의서에 명시되어 있지 않지만, API 설계 완결성을 위해 제가 임의로 추가한 항목입니다. 필요 없으면 빼도 됩니다.

① POST /auth/refresh — MEM06(토큰 만료)이 명세에는 "만료되면 재로그인 요구"로만 되어 있는데, 실제 구현에서는 재로그인 없이 Refresh Token으로 갱신하는 게 UX상 일반적이라 추가했습니다.
② 공통 응답 포맷 / 에러 코드 표 — 명세서엔 없지만 프론트-백엔드 협업을 위해 표준화했습니다.
③ GET /sources/{id}/status (SSE) — SRC02_PROC04 "실시간 표시" 요구를 폴링이 아닌 SSE로 구현하도록 제안했습니다. 폴링 방식을 원하면 GET 목록 API로 대체 가능합니다.
④ 알림 읽음 처리 API (PATCH /notifications/{id}/read, /read-all) — "알림 목록 및 읽음 처리"(SCR12)에 필요할 것으로 판단해 추가했습니다.
⑤ PATCH /members/me/notification-settings — NOTI01의 "이메일 알림 수신 동의" 선택 데이터를 별도 수정 API로 분리했습니다.
⑥ 채팅 답변 스트리밍은 SSE(text/event-stream) 기준으로 설계했습니다. WebSocket 방식을 선호하면 구조 변경이 필요합니다.
확인이 필요한 부분
· 회원가입 항목 중 "주민번호 앞 1자리"는 개인정보보호 관점에서 실제 저장 여부/암호화 방식 논의가 필요해 보입니다.
· SCR06 비고에 있는 NT01은 요구사항 ID 목록(MEM/SRC/NB/CHAT/NOTI)에 없어서, NOTI01의 오타인지 확인이 필요합니다.
